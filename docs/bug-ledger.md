# Bug Ledger — Casa D'Karmen (and the voice-client onboarding process)

*Every bug we've caught bringing up the Karmen voice agent — and, more usefully,
the **process** bugs that make the NEXT voice client slower. Consult before each
stage and at every new-client kickoff. Append, never rewrite. Started 2026-07-05.*

Sibling ledgers: the engine's code-invariant bugs live in
`loga-agent-core/docs/bug-ledger.md` (B-series); the voice-fabrication classes
(V1/V2/V4/V7) referenced in `karmen-elevenlabs-rewire.md` live in the
agent-core voice ledger. This file holds the **client-onboarding / operability**
classes — the ones about getting a new brand live, not about the code.

## How to use this
- **At client kickoff / before a stage:** read the prevention rules below as a
  pre-flight checklist. Most delays on the next client will rhyme with one of these.
- **After a bug is caught:** add an entry — symptom, root cause, prevention rule,
  and who/what caught it. The prevention rule is the transferable asset.

## Ledger

### K1 — CREDENTIAL HANDOFF STALL
- **Symptom:** The whole ElevenLabs rewire was blocked for a session — no tool could be created, no prompt swapped — because the ElevenLabs API key never actually reached the builder.
- **Root cause:** The key was delivered by `!printf '…' > .el_key`, which **silently failed twice** (the file was empty/absent), and nothing checked that the key was readable before ElevenLabs work began. A missing credential surfaced only when the first API call failed, deep into the session.
- **Prevention rule:** At client kickoff, **verify the ElevenLabs key is readable before any ElevenLabs work** — `wc -c < .el_key` must return `> 20`. Treat an unreadable/short key as a hard stop, not a warning. Same check for every provider credential the stage needs (Supabase token, shared secret) — prove the credential loads before building on it.

### K2 — COWORK CANNOT CREATE ELEVENLABS TOOLS
- **Symptom:** Attempts to create/save the `get_daily_menu` webhook tool through Cowork's path did nothing — the tool never persisted with its auth header.
- **Root cause:** Cowork's ElevenLabs **MCP only updates prompt + voice**; it cannot create tools. And the ElevenLabs **website UI silently refuses to save a webhook tool that carries a raw `Authorization` header** (no error, just no save). Two dead ends that both *look* like success.
- **Prevention rule:** **ALL ElevenLabs tool creation and agent wiring goes through the ElevenLabs API (Claude Code)** — `POST /v1/convai/tools` then attach the returned `tool_id` to `prompt.tool_ids` via `PATCH /v1/convai/agents/{id}`. Never create/wire tools via Cowork's MCP or the browser UI. (Cowork's MCP is fine for reading config and for prompt/voice-only tweaks, and Cowork still owns live verification.)

### K3 — MULTI-SUPABASE-ORG BLINDSPOT
- **Symptom:** The Supabase MCP could not see the client's project at all — `list_projects` didn't include it, so MCP-based schema/seed/deploy were impossible.
- **Root cause:** The MCP is **scoped to the logamarketing org**. Casa D'Karmen's Supabase project (ref `edcjcehfedwxxucktxoj`) lives in a **separate org** (`nncpmrizsddribljpdlv`). A clone in a different org is invisible to the logamarketing-scoped MCP.
- **Prevention rule:** At intake, **record the client's Supabase org + project ref**. If the project is **not** in logamarketing, all DB/gateway work uses the **Supabase CLI (`--project-ref`) or the Management API** (`POST /v1/projects/<ref>/database/query`) with `SUPABASE_ACCESS_TOKEN` — **never the MCP**. Put the org/ref in the client's README and secrets inventory so the next session doesn't rediscover this the hard way.

### K4 — STALE-DAY SEED
- **Symptom:** The agent returned `menu_not_set` on a day the restaurant was open, as if no menu existed.
- **Root cause:** The daily menu was seeded for the **wrong local date** — 2026-07-04 when "today" in Sinaloa was already 2026-07-05. The gateway correctly resolves "today" in **America/Mazatlan** (UTC-7, no DST) and found zero rows for the real current date. Seeding against a UTC/laptop date, not the client's local date, produced a menu that existed but for yesterday.
- **Prevention rule:** **Seed and verify daily data against the client's CURRENT local date**, and confirm through **the gateway's own resolved "today"** (call `get_daily_menu` and check `service_date` == the client-local date with a non-empty menu). Never trust the host/laptop/UTC date for a client in another timezone. The `menu_not_set` path is working-as-designed truth-telling — the fix is the seed date, never a fallback to another day (that would resurrect B12).

### K5 — ORDER FIRED WITH EMPTY REQUIRED FIELDS (voice never-confirm gap)
- **Symptom:** In a simulated call, when the caller answered the drinks question with "sería todo, gracias," Karmen jumped straight to `order_ready` and fired the order with `cliente_nombre:""`, `telefono:""`, and a **fabricated** `modalidad:"pickup"` — the modality was never asked, name/phone never collected, and the mandatory spoken read-back of dishes+total was skipped. An unfulfillable order (no name, no callback number) reached the n8n webhook.
- **Root cause:** Two prompt gaps compounding. (1) The `order_ready` gate said only "después de que el cliente confirme," enumerating **zero** required fields — and the tool schema's `required` list is satisfied by **empty strings**, so `""` passes. (2) The final-confirmation trigger was the literal phrase "¿Sería todo?", which collides with the caller spontaneously saying "sería todo"; the model treated the caller's utterance as the confirmation and skipped the read-back. "No repitas el pedido" further licensed skipping it.
- **Prevention rule:** Gate `order_ready` on **actually-collected, non-empty, non-invented** values — enumerate them explicitly in the prompt (modalidad chosen by the caller, nombre, teléfono of 10 digits; + dirección and cash_amount if delivery). Require an explicit agent **read-back of dishes+total and a "sí/correcto"** before firing, *even if the caller already said "sería todo"* — and disambiguate that "sería todo" **in reply to the drinks question means "no drink," not "close the order."** A provider's `required` schema flag is NOT a runtime guard against empty strings — enforce presence in the prompt. Mirrors engine Stage 4C never-confirm and B16.

### K6 — PROMPT ASSUMED ALL THREE CATEGORIES ALWAYS PRESENT
- **Symptom:** The prompt hardcoded "hoy tengo comidas, bebidas y extras" and "SIEMPRE pregunta '¿Te gustaría agregar alguna bebida?'" — but `get_daily_menu` can return an empty `bebida` or `extra` category on a given day, so the agent would offer/announce a category it has nothing to read from (risking a self-contradiction or an invented item to satisfy its own offer).
- **Prevention rule:** Offer, announce, and read **only the categories the tool returned with ≥1 item today**; never mention or offer a category that came back empty. Applies to the menu-read line AND the bebidas/extras up-sell line.

### K7 — MODEL SPOKE ITS INTERNAL PROCESS OUT LOUD (brain leak)
- **Symptom:** On real calls Karmen narrated her internal process to the caller: "Un momento, **proceso** tu pedido…", "**envío** tu pedido para confirmar…", "**preparo** tu pedido…", "**lo anoto**…", "te **pregunto** las bebidas disponibles…", and once she literally spoke the word "**Silencio…**" (reading her own stage direction). The HIGIENE rule (don't read internal notes/tool names) did not stop it.
- **Root cause (from the transcripts, not a guess):** RULE #0 mandated "say a short line before **any** tool call, in the same turn." For `get_daily_menu` that yields a natural courtesy. But before `order_ready`/`end_call` there is no natural customer-facing line, so the model filled the mandated slot with **process-narration** of the internal action. LLM = gpt-5-mini, `reasoning_effort=minimal` — ruled OUT a reasoning/verbosity chain-of-thought leak; it was prompt-driven. The prohibited-words list ("proceso/anoto/registro") was overridden by the RULE #0 pressure.
- **Prevention rule:** Scope the pre-tool line to **lookup** tools only (`get_daily_menu`, `compute_total`); before `order_ready`/`end_call` the model announces **nothing** (its only pre-order_ready line is the fixed farewell). Add a hard rule: **everything the agent outputs is spoken directly to the customer** — it never narrates its plan, the order it is tracking, "el cliente quiere…", tool/field names, or its own stage directions (never says the word "silencio"). If a host wouldn't say it aloud, don't say it.
- **Addendum (2026-07-18, owner-directed cleanup pass): "te anoto" RESOLVED.** gpt-4.1 (K10's new primary) occasionally said "te anoto…" — customer-directed, but still this class. Prompt hardened: the "TODO LO QUE DICES ES PARA EL CLIENTE" section now bans **anotar/apuntar in any conjugation** (plus proceso/registro/envío/preparo tu pedido) AND gives a replacement behavior — accept with a warm "claro / va / perfecto, ¿algo más?" and move on; "Apunta lo que te den" reworded to "Quédate con lo que te den" so the prompt stops priming the verb. The leak harness now hunts all anotar/apuntar conjugations. Proof: 135 duplicate-agent turns (prompt alone) + 199 turns on the final combined config (see K10 addendum) — **0 process-narration hits in 334 agent turns**. Lesson: a banned-word list alone loses to natural-courtesy pressure; ban the verb AND hand the model the phrase to say instead.

### K8 — WRONG TOTAL FROM LLM MENTAL MATH (V2 violation)
- **Symptom:** On a real call (2× Chile relleno $120 + Aguacate extra $15 + $20 delivery = **$275**) Karmen spoke a total of "**trescientos setenta pesos**" ($370) and only corrected to $275 **after the caller did the arithmetic for her**. Totals were inconsistent across calls (right on some, wrong on others) — the signature of LLM mental math.
- **Root cause:** No compute-total tool existed; `get_daily_menu` returns per-item prices but the **sum** was left to the model. V2 says numbers come from tools, not the model — the arithmetic step violated it.
- **Prevention rule:** Compute the total **in code**, never in the model. Added a gateway `compute_total` action: it re-reads TODAY's `daily_menu` prices (authoritative, not the model's read), sums `price × qty` for each item deterministically, adds the flat delivery fee, and returns the exact `total` (+ `breakdown`, `all_matched`, `unmatched`). Wired as an ElevenLabs tool (`compute_total`). The prompt: **always** call `compute_total`, **read the exact `total` field**, **always** state it and ask "…¿es correcto?", and `order_ready` never fires until the caller confirms the total. If `all_matched=false`, do not quote — re-verify the `unmatched` items. Proven live: the exact $370 order now returns $275.

### K9 — DEFAULT-PICKUP TOTAL BEFORE MODE KNOWN (price flip-flop)
- **Symptom:** Karmen could quote a peso total before the caller ever chose pickup vs delivery; when delivery emerged a turn later, the recomputed total jumped +$20 — the spoken price flip-flopped mid-call.
- **Root cause:** `compute_total`'s `modalidad` input was **optional**. The handler coerced an absent/invalid value to `""`, computed `delivery_fee: 0`, and even **reported `modalidad:"pickup"`** in the response — a fulfillment mode the caller never chose (the same default-to-pickup fabrication shape as K5's `order_ready`). Only `order_ready` was gated on mode; nothing gated the *quote*. This is V2's sibling: the fee is a fact that must come from the caller's actual choice, never from a code default.
- **Prevention rule:** **A quote tool REQUIRES every input that changes the amount before it returns a speakable number.** `compute_total` now refuses to quote without a caller-chosen mode (`pickup|recoger|delivery|domicilio`): it returns `mode_missing:true` with a short Spanish ask-pickup-or-delivery instruction and **no total** (same ok:true/HTTP-200 shape as `all_matched:false`, so the instruction reaches the model). Prompt side: establish the modalidad BEFORE calling `compute_total`; on `mode_missing`, ask and recompute; never voice a total until mode is known. Cross-ref: voice ledger **V2** (numbers come from tool facts, never defaults/memory), K5, K8. Lockstep (V4): confirmed live 2026-07-17 — the ElevenLabs `compute_total` tool schema already lists `modalidad` in `required` (description steers the model to 'delivery'/'pickup'); per K5, a provider `required` flag still passes empty strings, so the gateway gate is the real guard. Natural spoken forms ("a domicilio", "para recoger") are accepted by stripping the leading preposition; ambiguous ones ("para llevar") deliberately fall to `mode_missing` — ask, never guess.

### K12 — KITCHEN TICKET DROPPED THE DISHES AND SHOWED THE WRONG TOTAL (payload-shape mismatch on a rebuilt path)
- **Symptom:** Karmen's FIRST real order on the new Stage-A path (#108: flautas $120 + Coca-Cola $25 + $20 delivery = **$165**) produced a correct DB row — but the **kitchen Telegram ticket listed only the drink and said "Total: $25."** The dishes and the delivery fee silently vanished from the ticket the kitchen actually cooks from. Caught only because the real order's n8n execution data was read end-to-end during Stage-A closeout, not because anything alarmed.
- **Root cause:** the Stage-A notify formatter was created as a **verbatim copy of the OLD `order_ready` formatter**, which reads `body.platillos` / `body.delivery_fee`. The new `submit_order` gateway sends the **DB-shaped** payload — `platillos_consumidos.items` / `cargo_envio` / `precio_total`. `bebidas` matched by coincidence (same key in both shapes), which is exactly why it looked like it worked: the drink appeared, so the ticket rendered "successfully" and every success check passed. Compounding it, the copied formatter **recomputed its own total from line items** instead of reading the server-verified `precio_total` — so a dropped item silently produced a wrong total instead of an error.
- **Why the Stage-A proof missed it:** every notify test used either a payload hand-written in the OLD shape (the standalone webhook probes) or checked only `ok:true` / `message_id` — i.e. *delivery* was verified, **content was never diffed against the order**. "Telegram accepted the message" is not "the kitchen got the right ticket."
- **Fix (2026-07-19):** formatter now reads BOTH shapes (new first, legacy fallback) and **uses `precio_total` verbatim whenever present**, only falling back to summing for the legacy path that carries no verified total. Emits `used_verified_total` so the source of the number is visible in execution data. Proven by replaying order #108's exact payload: ticket now shows flautas $120 + Coca-Cola $25 + envío $20 + **Total $165**. Legacy `order_ready` path re-tested and still renders correctly (shared Telegram node untouched).
- **Prevention rule:** **When a rebuilt path reuses a downstream formatter/consumer, diff the CONTENT it produces against the source record — never accept "the send succeeded" as proof.** A copied consumer silently assumes the old producer's field names; overlapping keys make partial breakage look like success. Any component that renders money must read the **verified** total from the authoritative producer, never recompute it (voice ledger V2) — recomputation converts a dropped field into a plausible wrong number instead of a loud failure. Add a content assertion (expected total + item count) to the notify test, not just an HTTP/delivery check.

### K13 — TTS-MODEL TRANSCRIPT ARTIFACT DEFEATED THE VERIFICATION JUDGES (false FAIL in sims; latent false NEGATIVE in the leak scanner)
- **Symptom:** the first regression-sim run on the `eleven_v3_conversational` (D) shipping config reported **R1/R2 FAIL — `exact_total@None`**, i.e. "she never spoke the total." The agent had in fact spoken both totals correctly: transcripts read `"dos cientos sesenta pesos"` (260) and `"dos cientos cuarenta pesos"` (240).
- **Root cause:** transcript text for this TTS model arrives with **spurious mid-word spaces at streaming chunk boundaries** — verbatim samples: `"tam ales gratinados"`, `"llev emos"`, `"¿Me reg alas tu nombre"`, `"dos cientos sesenta"`. No LLM emits `"tam ales"`, and the **spoken audio is correct** (Scribe-verified on the sibling expressive battery: the `[amable]` tag was consumed, words intact). The judges matched literal spaced forms (`doscientos sesenta`), so correct behavior read as a failure.
- **The dangerous half:** the same artifact in `karmen_leak_harness.py` cuts the opposite way. A leak marker split by a chunk boundary (`"an oto"` for the banned `anoto`) would **slip past the scanner entirely** — a false NEGATIVE reported as "0 leaks." The sims failed loudly; the leak scanner would have failed **silently**, which is strictly worse.
- **Fix (2026-07-20):** both scanners now match against a **despaced copy** of the text in addition to the raw text. Sims: `hit()` helper + despaced number/farewell patterns. Leak harness: every pattern also run despaced with `\b` anchors stripped (no word boundaries survive despacing), so the despaced pass can only ADD reviewable false positives, never hide a leak. Proven both directions: `"se lo an oto"` → **caught** (3 patterns, flagged `[despaced]`); `"los tam ales gratinados"` / `"dos cientos sesenta pesos"` → **not flagged**. Re-judging the ORIGINAL failing transcripts with the fix → both PASS at `exact_total@8`, confirming only the judge was broken.
- **Prevention rule:** **a verification judge is itself under test whenever the surface it reads changes** — a new TTS model, ASR provider, or transcript pipeline can reshape the text without changing behavior. When a gate fails on a config change, read the raw transcript and decide *judge vs. agent* before touching either. And any scanner whose job is to find forbidden content must be checked for false NEGATIVES against a deliberately mangled input, not just for its ability to pass clean text — "0 leaks" from an unproven scanner is not evidence of 0 leaks.

### K14 — **WITHDRAWN / NOT A BUG** — "invented" free Té de Jazmín was a REAL promo from the KB (my verification error; V5 / K11-drift class)
- **Original (WRONG) claim, 2026-07-20:** that Karmen fabricated a promotion by offering *"si recoges aquí, te llevas un té de jazmín gratis"*, on the reasoning that Té de Jazmín is a $25 `bebida` and the warm-v3 prompt contains no promo language.

- **My verification error — the actual lesson:** I grepped **only the system prompt** for promo language, found none, and concluded fabrication. The agent had **four KB documents attached** carrying the real hours, payment rules, delivery fee, and promotions; I never read them. *An agent's grounding is prompt + knowledge base + tool results. Checking one source and declaring the other two absent is not verification.*
- **The evidence I misread as proof of the bug was in fact proof of correctness:** the "reproducible" 3/3-pickup vs 0/3-delivery pattern was Karmen correctly applying a **pickup-only** rule. - **KB docs must NOT be deleted or treated as stale.** They carry the real hours (desayunos 8:00–11:30, comida 11:30–17:00, no cenas), payment rules (no transferencias), the $20 delivery fee, and the promotions. This is the **K11 drift class surfacing** (V5): KB content is authoritative business truth that lives outside the prompt and outside the menu tables, and an audit that only reads code and prompts will keep mistaking it for invention.
- **Prevention rule:** **before declaring any agent output fabricated, enumerate and read EVERY grounding source it has — system prompt, every attached KB document, and the tool results in that conversation.** Write the check as "which source does this come from?" not "is this in the prompt?". And when accusing an agent of inventing something, the burden of proof runs the other way: reproducibility and internal consistency are evidence the claim is *sourced*, and the owner is the authority on business terms — ask before writing a gate that enforces your assumption. A gate built on an unverified assumption does not protect the system; it enforces the error.

### K15 — HOURS ENFORCED ONLY ON TOOL PATHS: Karmen claimed "¡Claro que sí! Aquí seguimos" at 10 PM
- **Symptom:** with the V6 hours rules built and every gateway boundary passing (47/47 assertions), the CLOSED sample call still failed on the thing that matters most. Pinned to 22:00, asked *"¿Todavía están abiertos?"*, Karmen answered **"¡Claro que sí! [alegre] Aquí seguimos, y justo ahorita tenemos desayunos bien sabrosos."** — announcing an open restaurant, at night, offering breakfast.
- **Root cause:** the enforcement was attached to the three TOOL actions (`get_daily_menu` / `compute_total` / `submit_order`). **The transcript shows she never called a tool** — she answered "are you open?" straight from the prompt and KB. A caller can ask about hours, and be answered, without any tool ever firing, so tool-path gating structurally cannot cover it. The gateway was never consulted, so its correctness was irrelevant.
- **Why the boundary battery missed it:** the battery proved the gateway's ANSWERS were right at every boundary. It never asked whether the gateway would be **consulted at all**. Testing a guard's logic is not testing its reachability — 47 green assertions on an unreachable path still leave the door open.
- **Fix (2026-07-20):** the gateway now serves ElevenLabs' **conversation initiation webhook**, called at conversation start *before the agent speaks*. When closed it returns a `conversation_config_override` replacing BOTH `first_message` AND the entire system prompt with a closed-restaurant instruction set (say this one line, no menu, no order, no transfer, do not invent another schedule, end_call). She cannot claim to be open because she is never told she is. When open it injects a prompt extension naming the current window and the real hours; every state also ships `karmen_is_open` / `karmen_window` / `karmen_hours` dynamic variables. Verified per-agent-scoped by empirical probe (set on the duplicate, confirmed live stayed `null`) before being wired anywhere.
- **Prevention rule:** **for any rule enforced server-side, ask "what is the shortest conversational path that reaches this claim WITHOUT calling my code?"** — and close that path at conversation start, not at tool time. Voice agents answer from prompt + KB by default; a tool is an option the model may decline to take, so tool-gated enforcement is advisory for exactly the questions (hours, location, policy) most likely to be answered conversationally. Corollary: a state test must exercise the state through the **caller's** route (ask the question) and not only through the API the state is implemented in — the sample call caught in one turn what a fully green boundary battery could not.

### K16 — THE SHADOW LAYER THAT COULDN'T FAIL (decorative pre-cutover instrumentation)
- **Symptom:** the V6 hours rules shipped behind a default-off flag with "shadow logging" so the cutover could be validated against real traffic (the V17 pattern). At cutover-prep the shadow rows looked healthy — but `get_daily_menu` logged `window_item_count == item_count` (61 == 61) in BOTH the desayuno and comida windows, and every pre-cutover `compute_total`/`submit_order` logged `window: null`. The layer meant to prove the rule's effect **could not, by construction, show any effect** — and it was about to be signed off as "clean."
- **Root cause:** every shadow field was derived from the **enforced** window, which is `null` while unenforced. `window_item_count` came from an unfiltered `allowed = [...CATEGORIES]`, so it always equalled the raw count; the off-window sets were computed inside `enforced ? … : []`, so pre-cutover they were never evaluated at all — zero coverage on the one path that refuses a paying customer.
- **Fix (2026-07-20):** compute the simulated decision **unconditionally** against `serviceWindow(now)` (observation), gate only the ACTION on the flag. Because the enforced and clock windows are equal by construction when enforcement is on, one code path serves both modes and live behaviour is byte-identical. Then the shadow log genuinely differs from unfiltered (61 vs 37) and names would-block items. Same defect existed on the WRITE path and was found only on a re-read after fixing the read path. New tool `scripts/shadow_hours_report.py` carries a guard that FAILS LOUD if `window_item_count` never differs from `item_count`.
- **Prevention rule:** **a shadow / dry-run / "would have done" layer must exercise the REAL rule against the REAL clock, and you must ASSERT its output DIFFERS from the unfiltered output — else it is decorative, and decorative shadow data is worse than none** (it converts "no evidence" into "evidence"). Audit the simulation on EVERY gated path, not just the first. The tell is uniformity: identical values across conditions that should differ (61/61 in two windows) means the rule is not running — the mirror of K14's "suspicious consistency means it IS running." Generalized as voice-ledger **V18** / stage-loop **scar 33**.

### K17 — THE OTHER WRITER: web orders land as anonymous "voice" orders (Parlanchin Code-node mapping bug)
- **Symptom:** row #118 in `ordenes_agente_voz` (2026-07-20 13:32 MZT) had a real order ($145 Lomo Mechado + Coca) but **null `cliente_nombre`/`telefono`/`modalidad`/`metodo_de_pago`** and `proveniencia: "Agente de Voz"`, with **zero gateway telemetry** — briefly suspected to be a rogue/direct insert. Rows 100–103 share the shape.
- **Root cause:** the order didn't come from the voice path at all. It is a **real customer web order** from menudeldia.casadkarmen.com, ingested by the n8n **Karmen Parlanchin** workflow (exec 70005 brackets the row's timestamp to the second). Parlanchin's Code node receives the full customer data in the webhook body but **builds the DB insert payload with those fields nulled** and **hardcodes `proveniencia: "Agente de Voz"`**. The kitchen Telegram node reads the body directly, so tickets are correct — the defect is invisible in operations and only corrupts the DB record.
- **Fix:** correct the Code-node mapping (pass through `cliente_nombre`, `telefono`, `modalidad`, `metodo_de_pago`; set `proveniencia` from the body's `Sitio Web`). **Deliberately not applied autonomously** — it is a live revenue path and no one was watching the line; needs a supervised edit + one test order.
- **Prevention rule:** **enumerate every writer to a shared table before reasoning about any row in it** — "no telemetry from MY path" means *another path wrote it*, not that the row is fake. K5's field-completeness gate was enforced only in the voice gateway; any parallel ingestion path (web, WhatsApp, dashboard) into the same table needs the same gate, ideally as a DB constraint (`NOT NULL` / check) so no writer can silently degrade. Corollary: a row that looks like garbage may be a paying customer — **provenance before deletion, always** (this is why the delete-authorized list was ignored for 100–103/118, correctly).

## Pre-flight checklist (derived from the ledger)
1. **Credentials load?** ElevenLabs key `wc -c > 20`; Supabase token present; shared secret present — **before** any build (K1).
2. **Which Supabase org?** Record org + project ref at intake; if not logamarketing → CLI / Management API only, never MCP (K3).
3. **ElevenLabs tools?** Create + wire via the **API**, never MCP or the web UI (K2).
4. **Daily data seeded for the right day?** Seed against the **client-local** date; verify via the gateway's resolved `service_date` (K4).
5. **Resolve "today" in the client TZ, never UTC** — and never serve a stale day; `menu_not_set` is the correct honest state (K4, engine B12).
6. **Prove with the live surface, not a code read** — auth (401 on missing/wrong secret), happy path, and one real call (K1/K4; engine meta-lesson).
7. **Order-firing tool hard-gated?** The order tool (`order_ready`) must NEVER fire without non-empty, caller-collected PLATILLOS + modalidad + nombre + teléfono (+ dirección-con-entre-calles + cash_amount if delivery) and an explicit spoken read-back + "sí" — a provider `required` flag passes empty strings, so enforce presence in the prompt (K5). Offer only categories the tool returned with items (K6).
8. **Total computed by the system, never the model** — read a `compute_total` tool's exact number; never let the model do order arithmetic (K8). State the total and ask "¿es correcto?"; `order_ready` waits on that "sí".
9. **Everything the agent says is spoken to the customer** — never let it narrate its process, order-tracking, tool/field names, or its own stage directions; scope pre-tool fillers to lookup tools only (K7).
10. **Before calling any agent output a hallucination, read ALL its grounding sources** — system prompt + every attached KB doc + that conversation's tool results. K14: a "fabricated" free-tea promo was real, owner-authored, and sitting in the Información KB doc. Consistency across runs (3/3 pickup, 0/3 delivery) is evidence of RETRIEVAL, not invention. Ask the owner before writing a gate that enforces your assumption.
11. **Never delete a knowledge source before reading its content** — KB docs carry hours, payment rules, delivery fees and promos that exist nowhere else in code or DB.
12. **Verify the exact provider model/API id for the exact surface before any conclusion that costs money** — `eleven_v3` (narration) is rejected on agents; `eleven_v3_conversational` works on Creator. A bogus value returns the accepted enum; confirm at runtime, not just config time.
13. **When live and duplicate share a backend, ship behind a default-off flag with shadow logging** (`KARMEN_HOURS_ENFORCED`) — a deploy otherwise changes live instantly (K15/V17). Prove both halves after deploy.
14. **Gate at conversation initiation, not only on tool calls** — "¿están abiertos?" fires no tool. 47 green boundary assertions coexisted with her claiming to be open at 10 PM (K15).
15. **Despace every content regex and prove scanners in the false-negative direction** — this TTS model splits words ("tam ales", "cortes ía") and defeated three separate judges (K13). Re-scan saved transcripts with the current scanner; a battery's `scan()` is loaded at process start.
16. **Definition of done is ONE REAL PHONE CALL** — it caught what every green battery missed, at every single stage.
